# Project profile

## About

- What this repository is: `mattermind`, a command-line tool, published on PyPI, that answers natural-language questions about a Mattermost workspace. An LLM with tool calling searches one team over the REST API v4, reads whole threads, follows the permalinks it finds in them and cites them in the answer. Its config loader, Mattermost client and agent loop can also be used from Python. That API is async only.
- Who uses it: people who want answers from their team's Mattermost history in a terminal (`mattermind ask`, or the `mattermind chat` TUI), and scripts that call it with `--json`.
- Language, version and main frameworks: Python 3.12 and newer. Typer for the CLI, Rich and Textual for output and the TUI, httpx for the Mattermost client, the `openai` SDK for any OpenAI-compatible endpoint, Pydantic for config. The code is in `src/mattermind/` and is built with hatchling.
- Where the documentation lives: https://bedrock-python.github.io/mattermind/, built with Zensical from `docs/` (`zensical.toml`). The API reference is generated from docstrings. `docs/agents.md` is the one-page reference for coding assistants.

## Commands

| Task | Command |
|---|---|
| Install dependencies | `make install` (`uv sync --extra dev`). `dev` and `docs` are extras, not dependency groups. Then install the hooks: `uv run pre-commit install --hook-type pre-commit --hook-type commit-msg`. |
| Format | `make fmt`: `uv run ruff format src/ tests/`, then `uv run ruff check --fix src/ tests/` |
| Lint and type-check | `make check`: `uv run ruff check src/ tests/`, `uv run ruff format --check src/ tests/`, `uv run mypy src/`. CI's lint job runs the same three. |
| Test | `make test` runs `uv run pytest -m unit` with coverage and `--cov-fail-under=80`. `make test-unit` runs the same tests without coverage. CI runs the unit tests with the same coverage threshold on Python 3.12, 3.13 and 3.14. |
| Run locally | `uv run mattermind --help` and `uv run mattermind version` need nothing. `uv run mattermind ask "<question>"`, `chat`, `teams` and `config validate` need a Mattermost server and an LLM endpoint, set in `~/.config/mattermind/config.yaml`, in `MATTERMIND_*` variables or in a file given with `-c <path>` (see `config.example.yaml`). The docs: `make docs-serve`. |
| Stop the local run | Ctrl+C. It ends `ask`, `make docs-serve` and the `chat` TUI. In the TUI, Escape cancels only the running query. |

## Conventions

- Default branch: `master`. A repository ruleset lets changes into it only through a pull request with the `All checks passed` check green. The pre-commit hook `no-commit-to-branch` refuses local commits to it.
- Issue tracker: GitHub Issues of this repository; refer to an issue as `#123`.
- Branch names: `<type>/<short-description>`, such as `fix/agents-page-findings`, as on every past pull request (CONTRIBUTING.md).
- Commit messages: Conventional Commits, `<type>(scope): <message>` (CONTRIBUTING.md), enforced by the `conventional-pre-commit` hook. Pull requests are squash-merged and release-please reads the squash commit, so a pull request's title must be a Conventional Commit too. A breaking change carries a `BREAKING CHANGE:` footer.
- Language of pull request titles and descriptions: English.
- Where specs and design notes go: in the pull request description; the repository has no place for them.

## Boundaries

- `CHANGELOG.md` is generated by release-please: never edit it by hand.
- The version lives in three places: `version` in `pyproject.toml`, the line marked `# x-release-please-version` in `src/mattermind/__version__.py`, and `.release-please-manifest.json`. release-please bumps all three; never change them by hand.
- `docs/agents.md` is part of the public surface. It changes in the same pull request as the CLI, the config models or the Python API (CONTRIBUTING.md, "The agents page").
- Files from the engineering-assets hub (`AGENTS.md` explains how it works):
  - the copy-page files: `docs/assets/javascripts/copy-page.js`, `docs/assets/stylesheets/copy-page.css`, `overrides/main.html`, `scripts/emit_markdown.py`;
  - `.github/workflows/release-please.yml`;
  - `.github/dependabot.yml`;
  - `.editorconfig`;
  - `CODE_OF_CONDUCT.md`.

  Change them in the hub; a change here makes the file this repository's own. `.github/workflows/docs.yml` is already this repository's own: its docs dependencies are the `docs` extra.
- Never publish to PyPI or create a release by hand: release-please creates the release, and `publish.yml` publishes it. Never dispatch `publish.yml` by hand. Never run `scripts/setup_repo.py`: it changes the GitHub repository's settings.
- Never read or print `~/.config/mattermind/config.yaml`, `.env` or the `MATTERMIND_*` variables. They hold the user's Mattermost token or password and LLM API key. `mattermind config show` masks them.
- `make test-integration`, `make test-all` and the commands `ask`, `chat`, `teams` and `config validate` send requests to the user's real Mattermost and LLM. Run them only when the user asks.

## Notes

- Releases: release-please opens its pull request with the workflow's own token, so CI does not start on it. Close and reopen the release pull request to run CI, then merge it. When the Release Please run on `master` completes and a `mattermind-v<version>` tag points at its commit, `publish.yml` publishes to PyPI. Only `feat`, `fix`, `perf` and `revert` commits make a release; the other types are hidden in `release-please-config.json`. Before 1.0, a breaking change bumps the minor version.
- Tests: every test carries the marker `unit` or `integration` (`--strict-markers`). Unit tests mock HTTP with respx and mocks and never touch the network. `tests/integration/` needs a real Mattermost and LLM, configured the same way as the CLI. No test needs Docker. Test names follow `test__<subject>__<condition>__<expected>`.
- On Windows, `test__config_show__config_flag_after_subcommand__reads_that_file` fails because it compares a Windows path with JSON-escaped output. CI runs on Ubuntu.
- Architecture, under `src/mattermind/`:
  - `cli/`: the Typer app;
  - `config/`: Pydantic models, a YAML loader with `${VAR}` interpolation, the `init` wizard;
  - `mattermost/`: the async httpx client;
  - `agent/`: the loop, tools, prompts and state;
  - `ui/`: Rich rendering and the Textual TUI.

  Config is applied in this order: defaults, then the YAML file, then `MATTERMIND_*` variables, then CLI flags; each later source overrides the earlier one. Unknown keys fail validation.
- `.env.example` lists the variables, but nothing loads a `.env` file. `mattermind init` always writes `~/.config/mattermind/config.yaml` and ignores `-c`. `login` and `teams` write the file given with `-c`, or the default one.
- Code style (CONTRIBUTING.md, `pyproject.toml`): type hints on every function (mypy `disallow_untyped_defs`); no `datetime.utcnow()`; no TODO or FIXME; lines up to 120 characters; double quotes; Google-style docstrings, which the API reference renders.
- `make fmt` and `make check` cover only `src/` and `tests/`. The pre-commit ruff hooks check every staged Python file, and `scripts/setup_repo.py` does not pass them.
